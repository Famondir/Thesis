Extraction of tabular data from annual reports with LLMs

4 Implementation

This chapter describes the practical realization of the methods and workflows developed for automated page identification and information extraction in financial documents. It outlines the environment our experiments are conducted in, the software packages utilized and the datasets created for benchmarking and evaluation.

It presents details of the ground truth creation process, including annotation strategies and dataset composition. The data processing workflow is illustrated, highlighting the system experimental setup on the Datexis Kubernetes cluster as wellas the local environment, used for evaluation and reporting.

By documenting the technical decisions and solutions adopted, this chapter provides a comprehensive overview of how the proposed methodology was translated into a functional system. We hope this will facilitate reproducibility and serve as a reference for future work. We especially want to recommend the use open-source scientific and technical publishing systems, like R Markdown and Quarto, to create documents that are directly linked to the data and code used for the analysis.

4.1 Environments

All computations for this thesis are conducted in two distinct environments. Tasks that do not require a GPU are executed locally; the specifications of the local device are provided in Appendix 12.2. Tasks necessitating a GPU are performed on the Datexis Kubernetes cluster.

We perform prototyping for most tasks on the cluster as well. Therefore, an interactive docker image with SSH (secure shell) capabilities and Python has been created based on the vLLM docker image. In rare cases a vLLM server is deployed on the cluster and queried from the local machine.

The experiments use the same images as the prototyping environment and connect to a persistent volume, where the scripts to run and data(bases) to use are located. It saves the results on the persistent volume, too. We fill 5 TB of persistent storage. Most of the space is used for caching the LLMs safetensors.

We do backups of the folder holding the scripts and data to process and download the results via SSH protocol. We use git for version control but do not synchronize the data from the persistent volume with GitHub. Within the local environment we use git as well. We synchronize all the data stored locally to a GitHub repository, except for the 10 GB of json formatted raw results.

4.2 Software Packages

4.2.0.0.1 Python

We use vLLM and chromadb to set up our in-context learning pipeline. vLLM is a fast and easy to use framework to provide LLMs locally or as service. chromadb is a vector database and key component of our naive RAG architecture (Gao et al., 2024). It provides the LLMs with examples that are most similar regarding their vector representations.

For data wrangling we use pandas. We save our experiments results using the json library. We extract texts from PDFs mainly with pypdfium2 and use sklearn for building RF classifiers.

4.2.0.0.2 R

We use the tidyverse library for data wrangling and to create our visualizations with ggplot. We use h2o for building RF models on the Datexis cluster and shapviz to interpret these models. knitr is used to create this thesis document.

4.3 Ground Truth Datasets

4.3.1 Ground Truth Creation

This section describes the ground truth creation process in detail. It describes our initial annotation process and what improvements are made, based on later iterations and findings from the experiments.

4.3.1.0.1 Page Identification

We search for the target pages in the chosen documents either by using the search functionality, the TOC or by scrolling through all pages. For each target page the filepath, page and type is listed in a csv (comma separated values) file. In some reports we find multiple pages for a single target type. In this case, all pages are added to the ground truth. Sometimes the Aktiva and Passiva table are on a single page. In this case a single entry is made and its type is noted as Aktiva&Passiva. If a single table spans two pages, both pages are recorded. We created 252 entries, excluding all pages that need OCR processing.

For double checking, all identified pages are extracted from their original PDF files and combined in a single file. Thus, problems with the numbers shown in the PDF viewer and the actual page number in the file are identified and resolved. We inspect pages that are classified as target by multiple models in the first experiments. Thus, we identify additional target tables, that span two pages.

In an earlier created sample of pages, we identified all pages that contain a table of any type. This smaller sample is based on all pages that are classified as containing a table of type Aktiva, Passiva or GuV with the regex approach. The true as well as the false positive classified ones. This ground truth is used to test the capabilities of various Python libraries, LLMs and visual models to detect tables. Results can be found in the Appendix 12.3.2.

4.3.1.0.2 Information Extraction

We manually copy the numeric values from the annual reports into csv files and replace the thousands separators and floating point delimiters. We multiply the values by 1_000, if a currency unit is given for the column the value comes from. The csv files are already prefilled with all entities defined in the legal text, identified by their full hierarchy.

There are cases, where a single line defined in the legal text is split up into multiple lines in the annual reports. In those cases, we write the corresponding sum into the most suitable row in the csv file. If entities are found, that do not fit any entity given in the legal text, this entry is dropped. In the first iteration the csv files are not prefilled with numeric values.

In the second iteration the csv files already contain the predictions of Qwen3-235B. We check the values, highlight mistakes, correct wrong values and log all mistakes found. In this iteration, we also check the ground truth created in the first iteration and identify mistakes made earlier.

Additionally, we implement an algorithm to generate synthetic Aktiva tables with systematically varied characteristics to enable experiments that investigate those characteristics as possible predictors for the extraction performance. Additionally, this enables us to estimate an upper limit for the extraction performance with real Aktiva tables.

4.3.1.0.3 Error Rate Guidance

There is no separate ground truth for the calculated confidence scores. We will investigate, if the true and false predictions can be discriminated based on the returned confidence scores. If a prediction is true or false is determined using the previously described ground truth datasets.

4.3.2.0.2 Information Extraction

It takes us up to 12 minutes per table to copy over all values from the PDF document into the csv file. The maximum amount of values to copy and format (or type manually) among the tables used is 40. In addition to this manual process, a conceptional process can be necessary, because the values have to be matched with the strict grammar. Sometimes we have to decide that there is no suitable row for a value and drop it. Sometimes there are multiple values that have to get summed up in order to calculate a value that suits the predefined schema.

This manual work is done for 36 documents. We include a single Aktiva table from every company that reports the balance sheet in the granularity matching our schema. We include additional documents Amt für Statistik und Brandenburg to check, if the in-context learning approach yields better performance, if examples from the same company the subject of extraction is from are used.

Later, the predictions of the LLMs are used, to create additional 70 ground truth tables. The old ground truth tables are checked in this iteration. We find an error rate of 2.4 %. Thus, the human reference score for percentage of correct predictions is 0.976. 4.4 Data Processing

This section describes the data flow for LLM approaches. Figure 4.3 visualizes the different processing steps. On the blue area the data flow of the benchmark is presented, starting with the PDF of an annual report as input and ending with the json formatted benchmark results as output. The green area shows how R is used to visualize the results for our analysis and interpretation. We use R Markdown to document the results in this thesis.

Figure 4.3: Showing the processing steps from input data to the results in this thesis.

We start by extracting the text for each page from the annual reports, using PDF extraction libraries like pdfium and pymupdf. We do this once for each document and save all text extracts page-wise in a json file. We record the original file path and corresponding pagenumber as meta data.

We embed the text extracts in the prompt template — either in the text section at the end or as an example in the blank section (see Figure 3.4). The prompt is then processed by the algorithm, predicting, if the text contains a specific type of information or not. The predictions are compared with the ground truth.

The results of this evaluation are saved as json. We save the result for every individual evaluation, as well as calculated performance metrics and the runtime needed to process all texts as batch. This allows us to reevaluate or exclude specific results and recalculate the aggregated metrics later. All steps from the text extraction to the result saving are implemented in Python.

The process for the information extraction is similar. One difference is, that the algorithm makes multiple predictions per text. Thus, we do not save a single prediction and its evaluation result but a data frame with all predictions and all ground truth values. Saving the ground truth values in this data frame is not necessary but allows us a more convenient reevaluation.

4.5 Evaluation and Reporting

We mostly use R for evaluation, visualization and reporting. We use the bookdown library4, to create a report, that is linked to our data and thus automatically includes new results and updates all figures and tables if the data changes. This allows us to run small additional experiments until the very end of thesis writing.

Furthermore, this allows us to create a PDF version and a HTML (hyper text markup language) version of the thesis at the same time with low additional effort. The HTML version can include interactive elements as paginated tables with search and sorting capabilities, image light boxes and image sliders. Thus, a lot of information can be offered without occupying too many pages with tables and figures. The HTML version is more machine-readable as well.

4.6 Speedup With vLLM and Batching

We run our final experiments with the vLLM library on Python, using its batch processing capabilities. Our first test used the transformers library directly and did not use batch processing. The runtime reduction that is achieved with the final setup can be found in the Appendix 12.3.3.

4.7 Hardware Normalization

To make the runtime of different LLMs running on different amounts and types of GPUs comparable, we conduct a benchmark running the models Qwen2.5-7B and Qwen2.5-32B with different hardware compositions on the Datexis cluster. Figure 4.4 shows the runtime for classifying 100 pages with the multi-class approach, providing three random examples for the in-context learning prompting strategy.

The classification time with Qwen2.5-32B on GPUs of type B200 is a little faster than running Qwen2.5-7B on the same amount of A100 GPUs. We calculate normalized runtimes for our experiments, based on these runtime measures for small and larger LLMs on different types and numbers of GPUs. One minute of computation on a single B200 is comparable to 4:30 minutes of computation on a single A100.

4.8 Summary

This chapter documented our choices and steps taken for implementing an experimental setup to evaluate the foundation for an automated system for page identification in and information extraction from financial documents.

Overall, the implementation successfully translated the proposed methodology into a functional and adaptable system, laying the foundation for subsequent evaluation and practical application.

The next section presents the key results obtained from the experiments conducted using this implementation. It highlights the performance of different models and approaches for both page identification and information extraction tasks, providing insights into their effectiveness and potential areas for improvement.
